# DR-03: First key through the quickstart

Measured: not yet. No run has produced a value.

| Field | Value |
|---|---|
| Name | First key through the quickstart (funnel stage 4) |
| The promise it proves | UC-01: the snippet turns the response into a working AES-256 key, never shown |
| Definition and formula | Accounts of the cohort with an `entropy_first_quickstart_success` at most 7 days after signup ÷ accounts of the cohort. Breakdown: by `client`, and the median minutes from `entropy_token_created` to it |
| Unit and aggregation window | A share of **accounts**; weekly signup cohort; read 7 days after the week ends |
| Data source, and where it is computed | `entropy_first_quickstart_success`, emitted by Qrypt's API on the first `200` whose `User-Agent` starts with `qrypt-quickstart-`; computed in Qrypt's analytics. A proxy: the key is made in the developer's process and never reported |
| Target, and the reasoning | 40%: **the project's own assumption**, four in five activations (NS-01's 50%) through the quickstart |
| What gaming looks like, and the guardrail | Another client copying the `User-Agent`, or the snippet sent by a test harness: [GR-01](/metrics/GR-01.md) shows whether those accounts come back, and DR-03 above NS-01 flags a fault |
| What decision changes when it moves | Low beside NS-01: developers call Qrypt their own way, and the snippets' languages or placement are reconsidered. One `client` far below the others: that language's snippet is fixed first |

The event and the rules every stage shares are in [the key metrics](/KEY_METRICS.md).[^key-metrics]
