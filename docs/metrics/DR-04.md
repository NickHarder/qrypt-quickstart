# DR-04: Agent success rate

Measured: not yet. The rounds run in Phase 8.

| Field | Value |
|---|---|
| Name | Agent success rate |
| The promise it proves | UC-03: an agent writes the program from the quickstart alone |
| Definition and formula | Runs logged as success ÷ runs in the round. Success: the program the agent wrote printed the success line with a working key, never the key, in a fresh container |
| Unit and aggregation window | A share of **runs**, per round of 5; the target is read on the revised round, and both rounds are reported |
| Data source, and where it is computed | `evidence/agent_runs.csv`, written by `make agent-round` (`src/qrypt_quickstart/agent_harness.py`); counted into `AGENT_READINESS.md`, which `tests/test_agent_readiness.py` keeps equal to the log. 2026-10-20: 5 of 5 in round 1 and in the revised round 2 against the mock, and 5 of 5 in round 2-live against Qrypt. The `agent-contract` eval cases, which feed it in replay, wait in `evals/pending/` for their recording |
| Target, and the reasoning | At least 4 of 5 in the revised round: **the brief's acceptance**[^assessment] |
| What gaming looks like, and the guardrail | Rerunning a failed run until it passes, dropping a `harness` failure, or a doc so long the agent takes half an hour: every run is logged as it happened, and [GR-02](/metrics/GR-02.md) caps the time |
| What decision changes when it moves | Under 4 of 5: each failure category becomes a regression case and a doc fix before anything else. At 5 of 5 in both rounds: `llms.txt` is left as it is and the effort goes to the human funnel |

Agents are a share of first-run developers (P-02), so a docs change that lifts this rate is expected
to lift [NS-01](/metrics/NS-01.md); how large that share is, nothing committed says.

The overview of every metric is in [the key metrics](/KEY_METRICS.md).[^key-metrics]
